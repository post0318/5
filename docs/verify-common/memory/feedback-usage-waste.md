사용량을 아끼되 병렬 진행 자체는 문제 삼지 않는다 — **단 SEC 조회가 많은 작업은 순차**(오너 2026-09-26 — "병렬처리하지말고 순차적으로. 중단 풀리는 시간 감안하면 병렬로 하면 손해다": 병렬 에이전트가 SEC Archives 429 차단을 유발, 앱이 틀린 값을 냄). 낭비는 따로 있다: 같은 조사 반복, 이미 정한 방향 재질문, 가벼운 작업(문서 정리·스크립트 작성)에 무거운 모델, 곧 교체될 코드의 감사.

오너가 짚은 가장 큰 낭비(2026-09-25): **"재검증 반복이 문제였다"** — 수정할 때마다 검증 스크립트를 수십 종목씩 돌리고(에이전트마다 자기 확인용으로 또 돌림), 전체 47종목 재검증·재감사를 여러 번 반복했다. 앞으로: 수정 중 확인은 해당 종목 1~2개·해당 항목만, 에이전트에게 "검증 실행"을 기본으로 시키지 말 것, 전체 재검증은 지표를 닫을 때 1회.

**Why:** 2026-09-25 세션 한도 소진(오전 11시 리셋까지 중단) 후 오너 — "쓸데없는 짓해서 사용량 부족뜨고", 이어서 "병렬진행은 문제가 아니다".

**How to apply:** 독립 작업은 병렬로. 조사 산출물은 파일로 남겨 재사용(scratchpad 에 경로 기록). 모델: 문서·단순 구현 sonnet, 설계 판단·감사 opus. 감사는 지표를 닫을 때 한 번. 결정된 사항은 메모리·문서에 적고 다시 묻지 않는다. 관련: [[feedback-batch-fix-then-verify]]
