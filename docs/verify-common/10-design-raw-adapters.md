## 0. 요약

- ①은 **시장별 원천에서 받아 디스크에 보관하고, 판독해서 "원자료 사실(RawFact)"과 "정규화 항목(Item)"을 낸다.** 계산(LTM·비율·대체)은 하지 않는다. 계산은 ④가 ①의 출력만으로 한다.
- 세 시장의 출력 형식은 하나다(§2). 시장 차이는 입력 원천과 판독 규칙(§4~§6)에만 있다.
- **판본은 지우지 않는다.** 모든 사실에 출처 서류(접수번호·accn·docID)와 "처음 공시 / 최신 판본" 표시를 붙인다. 어느 판본을 쓸지는 ④가 정한다. 기본은 최신 판본이고, 예외는 Q2 이자비용(분자와 같은 보고서)·분할 수정 기준이다.
- 조회 실패는 **검증불가**다. "자료 없음을 확인한 것"만 기대 빈칸으로 넘긴다. 둘을 섞지 않는다(§3.4).
- 캐시는 오너 결정 그대로 따른다: 지우지 않음, 옛 판본 보관, 90일 미사용 삭제 없음, 5GB 넘을 때만 오래 안 쓴 것부터 정리하고 건수를 기록. **지금 코드는 세 곳 모두 이 결정과 다르다**(§8 C1~C6).
- 앱 코드·앱 데이터 파일을 쓰지 않는다(공통모드 방지). 지금 검증기는 한 곳에서 앱 데이터 파일을 읽는다(§8 C11).
- **원본은 앱과 같은 보관소 하나를 쓴다(오너 결정 2026-10-15)** — 공통모드는 같은 원본이 아니라 같은 판독 규칙에서 생긴다. 판독 결과(파생)는 공유하지 않는다. 대신 저장 때 형식 검사·읽을 때 공시 신원 확인·갱신형 응답 해시 판본을 둔다(§1.3·§3.5 공유 원본 보관소).

## 1. 범위와 경계

### 1.1 ①이 하는 일
1. 원천 호출(요청 한도·간격 지킴) → 원본 바이트를 디스크에 판본별로 보관.
2. 원본 판독(파싱): XBRL 인스턴스·계산 구조(`_cal`)·표시 구조(`_pre`)·라벨(`_lab`), DART JSON·원문 HTML 표, EDINET XBRL·인라인 XBRL, KRX·공공데이터 JSON.
3. 사실 정규화: 단위(원 단위 정수), 기간(결산일 기준), 범위(연결/별도·지배/비지배·계속/중단), 판본(처음 공시/최신), 출처 위치.
4. 시장 고유 줄 식별: "이 줄이 본표의 유형자산 취득 줄인가" 같은 판독은 언어·공시 형식에 매여 있어서 ①에서 한다. 결과는 사전 부품 이름의 **항목 키**로 표시한다(§2.2). ④는 항목 키만 보고 시장을 모르는 채로 계산한다.
5. 실패 사유 기록(§3.4)과 요청 수 기록.

### 1.2 ①이 하지 않는 일
- LTM·평균·비율·배수·분할 보정 계산(④).
- 값이 없을 때 다른 원천·다른 정의·근사로 채우기. 그림자 채우기는 금지다(memory `feedback-no-shadow-fill`). ①은 빈칸과 사유를 그대로 넘긴다.
- 외부 사이트 값(③)과 앱 응답(②) 읽기.
- 판정(⑥).

### 1.3 독립성(공통모드 방지)
- `src/**` 아래 어떤 파일도 import·read 하지 않는다. 코드뿐 아니라 **데이터 파일도** 포함한다(예: `src/lib/markets/kr/data/corpcodes.json`, 앱 휴장일 표).
  이를 정적 검사로 막는다(eslint `no-restricted-imports` + `readFileSync` 경로 검사 — 구현 방식은 승인 뒤).
- **원본은 공유, 판독은 따로(오너 결정 2026-10-15 — 예전 「앱 캐시 폴더를 읽지 않는다, 검증기 캐시 루트는 따로」를 바꿈. `verify-jp-design.md` §0-5 도 이 결정으로 대체)**.
  - 오너 지적: 「같은 정의면 원본은 하나 — 불러오기만 하면 되지 않나」, 「(깨진 파일·엉뚱한 파일·시점 차이는) 설계와 실행에서 없도록 해야 하는 것이지 각각 받는다고 해결될 사안인가」. 확인 결과 따로 받기는 세 위험 어느 것도 막지 못한다 — ① 깨진 파일은 양쪽이 각자 받을 수 있고(동시 확률만 낮음) ② 주소 오류는 따로 받으면 앱 쪽 오류만 피하고 검증기 자신의 오류는 남으며 ③ 갱신형 응답은 따로 받으면 받은 시각이 달라 차이가 판본 탓인지 계산 탓인지 가리기 어렵다. 막는 것은 아래 세 검사다.
  - 앱과 검증기가 **원본 보관소 하나**(§3.5 「공유 원본 보관소」)를 쓴다. 누가 먼저 받든 같은 규칙으로 저장하고, 다른 쪽은 불러오기만 한다.
  - 공유하는 것은 **원본 바이트와 판본 색인뿐**. 판독 결과(걸러낸 사실·표·문장, 파생 파일)·앱 저장본(DB)·앱 메모리 캐시는 공유하지 않는다 — 판독 규칙이 같아지면 그것이 공통모드다.
  - 검증기는 원본을 읽을 때마다 **공시 신원 확인**을 직접 한다(누가 받았든). 앱이 엉뚱한 공시를 그 번호로 저장한 사고가 검증기로 번지지 않게 하는 장치이고, 검증기 자신의 주소 오류도 같이 막는다.
- 같은 공시를 읽는 것 자체는 공통모드가 아니다. 공통모드는 **앱과 같은 판독 규칙**으로 고른 값이다. 앱과 같은 규칙으로 고른 항목은 Item 에 `rule_shared_with_app: true` 를 달아 ⑥에 넘긴다.
  예: 한국 "연도별 최신 보고서", 일본 "가장 나중 서류" 판본 선택은 앱과 같은 원칙이다. 다만 판정 방법(문맥 이름 vs 값 있는 줄 수)이 다르면 독립으로 본다.
- 오너가 정한 정의(예외표)는 **문서로만** 공유한다. 앱·검증기가 같은 상수 파일을 import 하지 않는다(`00-handoff.md` "예외표는 오너 결정 문서").

`verify/common` 브랜치 `scripts/verify/raw/{common,us,kr,jp}/`. 지금은 미국 `scripts/verify-financials.mjs`, 한국 `scripts/verify-kr/*`, 일본 `scripts/verify-jp/*` 가 브랜치마다 따로 있다

### 2.1 RawFact — 원자료 사실 한 건(손실 없는 기록)

| 칸 | 내용 | 예 |
|---|---|---|
| `market` | `us`·`kr`·`jp` | |
| `entity` | 종목 코드 + 원천 식별자(CIK·DART corp_code·EDINET 코드) | `{sym:"005930", corp:"00126380"}` |
| `filing` | 출처 서류: `id`(accn·rcept_no·docID), `form`(10-K·10-Q·20-F·40-F·6-K / 11011·11012·11013·11014 / 120·130·140·150·160·170), `filed_at`, `period_end`(서류 기준일), `amends`(정정이면 원 서류 id), `withdrawn` | `{id:"20240312000736", form:"11011", ...}` |
| `concept` | 원천 식별자(태그·account_id·요소 ID·회사 고유면 `ext:`), 원문 라벨(영·한·일 그대로), 표준 여부 | `ifrs-full_PurchaseOfPropertyPlantAndEquipmentClassifiedAsInvestingActivities`, 「유형자산의 취득」 |
| `placement` | 본표 여부(`face`/`note`/`cover`/`summary`(경영지표)/`dividend`/`market`), 본표 종류(`bs`·`is`·`ci`·`cf`), 구역(영업·투자·재무, 유동·비유동), 부모 줄, 표시 순서, 표시 구조 역할 | `{face:true, stmt:"cf", section:"investing", parent:"..."}` |
| `period` | `kind`(duration/instant), `start`, `end`, `months`(실제 개월 수), `fy_key`(§3.1), `fp`(FY·H1·Q1·Q3·YTD9M·3M), `column`(당기·전기·전전기 / CurrentYear·Prior1Year·Interim… / 문맥 id) | |
| `scope` | `consolidation`(consolidated·separate), `attribution`(total·parent·nci·none), `ops`(total·continuing·discontinued·none), `dims`(남은 차원 목록 — 비어야 본표 값) | |
| `value` | `raw`(원문 문자열 그대로), `num`(정수 문자열 또는 원문 소수 문자열), `unit`(ISO 통화·`shares`·`ccy/share`·`pure`), `scale`(표 단위 배수 — 원문 표만), `decimals`(XBRL), `sign`(공시 부호 그대로 + `negated_label` 여부), `nil`(xsi:nil·「－」) | `{num:"98284827118", unit:"KRW", decimals:"-3"}` |

| `locator` | 원본 안 위치: XBRL `contextRef`+요소, fnltt 행(`sj_div`·`account_id`·열 이름), 원문 표(문서 파일·표 순번·행·열·표 앞 제목·단위 문구), 인라인 XBRL `id` | 사람이 원문에서 바로 찾을 수 있어야 한다 |
| `fetch` | 캐시 파일 경로·sha256·받은 시각·HTTP 상태·원천 상태 코드·어댑터 판·판독기 판 | |

원칙:
- 원본에 있는 숫자는 **판독 가능한 것은 모두** RawFact 로 남긴다. 고르는 일(어느 태그·어느 줄)은 Item 단계에서 한다. 판독 규칙이 바뀌어도 원문을 다시 받지 않게 하기 위해서다(오너 2026-10-05 "로직이 바뀌었다고 원문을 다시 받지 않는다", `scripts/lib/dart-disk-cache.mjs` 머리말).
- 숫자는 부동소수로 바꾸지 않는다. 금액은 원 단위 **정수 문자열**(표 단위 배수도 정수 곱), 주당 값은 원문 소수 문자열 그대로. 판정의 "정수 완전·소수 1e-14"(`00-handoff.md` 가)를 지키기 위해서다.
- 부호는 공시 그대로 둔다. 표시 부호(negatedLabel)는 따로 표시만 한다. CapEx 같은 지출 줄을 양수·음수 어느 쪽으로 쓸지는 ④가 정한다.

### 2.2 Item — 정규화 항목(①의 시장 규칙 적용 결과)

| 칸 | 내용 |
|---|---|
| `key` | 사전 부품 이름(예: `capex_ppe_line`, `interest_expense_pl`, `cash_cf_end`, `dividends_declared_parent`, `eps_diluted_total`, `shares_listed`, `ni_parent`, `oi`) — 확정판 `01-metric-dictionary.md` 를 따른다 |
| `period`·`scope` | RawFact 와 같은 형식 |
| `value` | 하나의 값 또는 빈칸 |
| `blank_reason` | 빈칸이면 사유 코드(§3.4) — "없음 확인"과 "판독 실패·조회 실패"를 구분 |
| `facts` | 근거 RawFact id 목록(합산이면 전부, 예: 일본 이자 구성요소) |
| `rule` | 적용한 규칙 번호(이 문서 §4~§6 의 R-번호)와 근거 결정(Q2·Q3·Q12 등) |
| `vintage_basis` | 어느 서류의 값인가(판본 선택은 ④가 하지만, Item 은 **서류마다 따로** 만든다 — 같은 기간 같은 키가 서류 수만큼 있을 수 있다) |
| `rule_shared_with_app` | 앱과 같은 판독 규칙이면 true(§1.3) |

Item 은 **서류(판본)별로** 만든다. 예: 한국 FY2022 영업이익은 FY2022 보고서 당기·FY2023 보고서 전기·FY2024 보고서 전전기, 이렇게 세 Item 이 될 수 있다. ④가 판본 규칙(§3.3)으로 하나를 고른다.

### 2.3 그 밖의 출력
- `Filing`: 서류 목록 행(정정·철회 포함, 원 서류 연결). 판본 판단의 근거다.
- `Event`: 주식 사건 — 액면분할·병합·무상증자·분사 `{date(효력일), ratio, kind, source}`. 분할 수정 기준(§3.3)의 입력이다.
- `MarketDay`: 시세 하루 — `{date, close(미보정 실제 종가), mcap, listed_shares, stock_kind}`(한국 KRX), 미국·일본은 §4·§6.
- `FxRate`: 환율 고시(미국 20-F 환산용) `{series, date, rate, source}`.
- `FetchLog`: 실행당 원천별 요청 수·캐시 적중·실패·정리 건수. 두 번째 실행의 요청 수가 0에 가까운지 확인하는 데 쓴다(memory `feedback-process-only-new`).

## 3. 공통 규칙

### 3.1 기간 판정
- 기간 열쇠는 **결산일**이다. 라벨 문자열("FY2026")로 맞추지 않는다. 미국 52/53주 결산 누락(WEN)을 겪었기 때문이다.
- `fy_key` = 결산일의 연도. 단 미국은 결산일이 1월 1~7일이면 전년도다(CLAUDE.md `fiscalYearOf`). 이 함수는 검증기가 따로 구현한다.
- `months` 는 실제 기간 길이다. 12개월이 아닌 사업연도(첫 회계기간 — SK스퀘어 FY2021 2개월, `06` 문서)는 `months` 로 드러낸다. 그런 칸을 쓸지는 ④가 정한다.
- 누적과 3개월 값을 구분한다. 한국 fnltt `thstrm_add_amount`(누적)와 `thstrm_amount`(3개월), 일본 `CurrentYTD`·`CurrentQuarter`, 미국 `start`~`end` 길이로 나눈다. 4분기 값·LTM 은 ④가 만든다.

### 3.2 연결/별도·지배/비지배·계속/중단
- 연결과 별도를 모두 받는다. Item 의 기본 범위는 연결이다. 그 해 연결 재무제표가 **없음을 확인한 해만** 별도 Item 을 내고 `scope.consolidation = separate` + 사유 `no_consolidated` 를 붙인다. 이것은 한국 앱 규칙과 같은 원칙이라 공통모드 표시 대상이다.
  연결 조회가 **실패**한 해에는 별도로 넘어가지 않는다. 검증불가다(앱 `dart-facts.ts:62` 주석과 같은 교훈).
- 지배/비지배는 원천 개념으로 정한다. 미국 `NetIncomeLoss` = 지배·`ProfitLoss` = 전체, 한국 `ProfitLossAttributableToOwnersOfParent`, 일본 `ProfitLossAttributableToOwnersOfParent*`.
  이름으로 추정하지 않는다. 지배 개념이 없고 계산식(전체 − 비지배)이 필요한 경우는 ④의 일이다. ①은 두 사실을 모두 낸다.
- 계속/중단: 계속영업 개념과 전체 개념을 따로 낸다. 중단영업 줄이 손익계산서에 있는지(`has_discontinued`)를 서류·기간마다 표시한다. Q2 이자비용(계속영업 범위)과 감가상각 같은 기준 원칙이 이 표시를 쓴다.

### 3.3 판본(재작성) 처리
- ①은 판본을 고르지 않는다. 모든 서류의 모든 열을 낸다. `is_original`·`is_latest`·`restated` 표시도 붙인다.
- ④의 선택 규칙(근거 결정 — ①이 무엇을 남겨야 하는지 정하려고 적는다):
  - 기본: **최신 판본**(미국 오너 결정 2026-09-25, 한국 "연도별 최신 보고서" CLAUDE.md, 일본 `verify-jp-design.md` J-A1).
  - **Q2 이자비용**: "이자비용은 분자 영업이익을 가져오는 보고서와 같은 보고서 값"(10-14, `01` 초안 §6). 그래서 ①은 이자 Item 을 서류별로 내야 한다.
  - **분할 수정 기준**(10-14 "액분은 수정기준"): 과거 열은 모두 현재 주식 기준이다. 재작성 EPS 와 분할 보정 종가를 쓴다. ①은 서류별 EPS·서류 제출일·Event(사건 효력일·비율)·미보정 종가를 낸다. 보정 계수는 ④가 계산한다.
- **판본을 잃지 않는 조건**: DART `fnlttSinglAcntAll`·`alotMatter` 는 같은 요청에 대해 **최신 판본만** 돌려준다. 정정 공시가 나오면 정정 전 값은 API 로 다시 받을 수 없다(`00-handoff.md` 캐시 결정의 근거).
  그래서 정정 전 판본 파일을 지우면 원공시 값을 되찾을 수 없다. 미국 companyfacts 는 사실마다 `accn`·`filed` 를 실어 옛 판본 값이 응답 안에 남는다. EDINET 은 정정이 새 docID 라 원 서류가 그대로 남는다.
  - 확인 필요(조사): DART `fnlttXbrl.xml` 을 정정 전 접수번호로 요청하면 정정 전 XBRL 을 지금도 받을 수 있는지. 받을 수 있으면 fnltt 옛 판본을 잃어도 XBRL 로 되찾을 수 있다. 확인하지 않았다.

### 3.5 캐시 (오너 결정 2026-10-11 — 그대로 옮김)
> 앱·적재·검증기 같은 규칙: 검증 로직이 지우지 않음, 옛 판본 보관(DART fnltt 는 최신 판본만 줘서 지우면 정정 전 값 복구 불가), 90일 미사용 삭제 없음, 5GB 상한 초과 때만 오래 안 쓴 것부터 정리 + 건수 기록.

구현 규칙(설계):
1. 배치 `<루트>/<시장>/<원천>/<요청 열쇠>/<판본>.<확장자>` + 요청마다 판본 색인 `index.jsonl`(판본 id·받은 시각·sha256·크기·HTTP/원천 상태·요청 URL(키 가림)).
   새 판본은 **추가만** 한다. 옛 판본 파일은 그대로 두고, 색인에 `superseded_by` 를 적는다.
2. 판본 id:
   - DART 보고서 응답(fnltt·alotMatter·stockTotqySttus 등) = 그 보고서의 최신 접수번호. 보고서가 없으면 `none`.
   - 접수번호로 받는 원본(XBRL·원문) = 접수번호. 바뀌지 않는다.
   - SEC Archives = accn(불변). companyfacts·submissions = **내용 sha256**. 내용이 같으면 새 파일을 만들지 않고 색인에 "확인 시각"만 남긴다.
   - EDINET 서류 = docID(불변). 날짜 목록은 확정일(JST 오늘 − 2일 이전)만 저장한다. KRX 하루 = 날짜(지난 날짜 불변, 게시 전 빈 응답은 저장 안 함).
3. 저장하지 않는 것: 조회 실패, 빈 본문, 깨진 JSON·zip, 000·013 외 DART 상태, EDINET status ≠ 200. 실패는 저장하지 않되 **기억**한다. DART 800 은 30분, 반복 실패는 실행 안에서 다시 요청하지 않는다(memory `feedback-process-only-new` 2026-10-10 재발 사례).
4. 쓰기는 임시 파일 → rename(원자적). 읽은 파일이 깨졌으면 **지우지 않고** `quarantine/` 로 옮긴 뒤 다시 받는다. 지금 코드는 지운다(§8). 이 문서는 "검증 로직이 지우지 않음"을 문자 그대로 적용했다.
5. 읽을 때 파일 시각을 갱신한다(LRU 판단 기준).
6. 정리: 실행 시작 때 1회. **90일 미사용 삭제는 없다.** 전체가 5GB 를 넘을 때만 오래 안 쓴 것부터 지운다. 지운 건수·크기·대상 종류를 실행 결과와 `cache-evictions.jsonl` 에 남긴다.
7. "자료 없음(013·none)"도 그때의 판본과 함께 저장한다. 목록에 보고서가 생기면 판본이 바뀌어 자연히 무효가 된다(지금 규칙 유지).
8. 갱신 주기("바뀌었을 수 있는 것"만): DART 회사 정기공시 목록 6시간, SEC companyfacts·submissions 12시간, EDINET 최근 2일 목록·KRX 오늘 자료는 실행마다. 나머지는 불변이라 다시 묻지 않는다.

**공유 원본 보관소(오너 결정 2026-10-15)** — 앱(2호기 verify-dev·적재 스크립트)과 검증기가 같은 루트를 쓴다. 운영 1호기에는 검증기가 없어 해당 없음(1호기 앱은 자기 캐시).

- **위치(오너 결정 2026-10-15 「고쳐라」)**: 루트 = `/home/ubuntu/raw-store`. 안은 1번 배치 그대로 — `raw-store/us/sec/…`, `raw-store/kr/dart/…`, `raw-store/kr/krx/…`, `raw-store/jp/edinet/…`, 격리는 `raw-store/quarantine/`, 정리 기록은 `raw-store/cache-evictions.jsonl`.
  - 앱은 `~/5/.env.local` 의 `SEC_CACHE_DIR`·`DART_CACHE_DIR`·`EDINET_CACHE_DIR` 를 이 루트로 바꾸고(C20), 검증기는 같은 루트를 설정 하나(`RAW_STORE_DIR`)로 읽는다. 루트를 코드에 박지 않는다.
  - 검증기 판독 결과(파생 파일)는 이 루트에 두지 않는다 — 검증기 쪽 `reports/.verify-derived/`(판독기 판별). 앱 파생도 앱 쪽에 둔다.
  - 5GB 상한(6번)은 **원천마다**(us/sec·kr/dart·jp/edinet 각각) 센다. 공유로 바뀌어도 D15 「저장소마다 5GB, 부족하면 상한을 올림」 그대로.
- **지금 폴더(10-15 2호기)와 옮기는 순서**: 앱 `~/sec-cache/sec-archives`·`sec-api`·`~/dart-cache`·`~/edinet-cache`, 검증기 `~/sec-cache/verify-archives`·`verify-api`·`~/5/reports/.dart-cache`. 모두 같은 디스크(`/dev/sda1`, 45GB 중 12GB 남음)라 옮기기는 rename 이고 공간이 더 들지 않는다.
  1. 앱 캐시를 새 배치로 옮긴다(파일마다 10번 형식 검사 + 11번 신원 확인을 통과한 것만, 실패는 `quarantine/`). 색인 `index.jsonl` 을 만든다.
  2. 검증기 사본 중 같은 열쇠가 루트에 없는 것만 같은 검사 후 옮긴다. 같은 열쇠가 있으면 sha256 비교 — 같으면 사본 삭제, 다르면 사고 기록 + 둘 다 `quarantine/`.
  3. **복구 불가 판본**(DART fnltt·alot 정정 전, D15)은 옮기기 전 따로 복사본을 떠 두고, 옮긴 뒤 건수·sha256 이 같음을 확인한 다음에만 옛 폴더를 지운다.
  4. 옛 폴더는 앱·검증기가 새 루트로 한 번씩 정상 실행한 뒤 지운다. 옮긴 건수·크기·격리 건수를 결과에 남긴다.
9. **대상**: 원본 전부 — 불변 원본(SEC Archives accn, DART 접수번호 원문·XBRL zip, EDINET docID zip, KRX 지난 날짜)과 갱신형 응답(SEC companyfacts·submissions, DART fnltt·alotMatter·목록, EDINET 날짜 목록). 판독 결과·파생 파일은 대상 아님(각자 따로 둔다).
10. **저장 때 형식 검사(받은 쪽이 한다, 통과한 것만 저장)**: 빈 본문·HTTP 오류·원천 오류 상태 거부(3번), XML 은 끝까지 파싱되는지(잘린 파일 거부), zip 은 CRC 전체 검사, JSON 은 파싱 + 원천별 필수 필드(companyfacts `cik`·`facts`, DART `status`). 거부한 것은 저장하지 않고 실패로 기억한다(3번). 색인에 sha256·크기·받은 쪽(app/verify)·받은 시각을 적는다.
11. **읽을 때 공시 신원 확인(읽는 쪽이 한다, 검증기는 매번)**: 파일 sha256 = 색인 값, 그리고 파일 **안의** 신원이 요청과 맞는지 — SEC 인스턴스 `dei:EntityCentralIndexKey`·`dei:DocumentType`·`dei:DocumentPeriodEndDate`, companyfacts `cik`, DART XBRL·원문 회사 고유번호·보고서 종류·사업연도(원문 표지), EDINET `edinetCode`·서류 종류·기간. 하나라도 다르면 그 파일을 쓰지 않고 `quarantine/` 로 옮긴 뒤 다시 받는다 + 사고 기록(받은 쪽 코드 결함 신호이므로 결과 파일에 남김). 다시 받아도 다르면 그 칸은 검증불가.
12. **갱신형 응답 = 내용 해시 판본, 추가만**(2번과 같음). 앱과 검증기는 각자 **어느 판본(sha256)을 썼는지** 기록한다. 대조 때 판본이 같으면 차이는 계산 차이, 다르면 판본 차이로 바로 가른다(따로 받던 때는 가를 수 없었다).
13. **동시 쓰기**: 같은 열쇠를 두 쪽이 동시에 받으면 임시 파일 → rename(4번)으로 먼저 끝난 쪽이 남고, 나중 쪽은 sha256 이 같으면 버리고 다르면(불변 원본인데 내용이 다름) 사고로 기록하고 두 파일 모두 `quarantine/`.
14. 효과(2호기 실측 10-15 기준 추정): SEC 원본 앱 3.4GB·검증기 4.0GB 가 한 벌로(약 3.5GB 감소), 같은 공시 이중 요청 없어짐. 한국 DART 원문·XBRL 도 앱 보관분(약 230MB)을 검증기가 불러옴(C9 의 「원본 보관」이 이것으로 해결).

**U1·U2 오너 결정(2026-10-15, `13-open-decisions.md` D15)**: 저장소(루트)마다 5GB, 복구 불가 판본(DART fnltt·alotMatter 정정 전)은 정리 대상에서 제외하고 용량도 따로 센다, 다시 받을 수 있는 것만 오래 안 쓴 순서로 정리. 용량이 부족하면 지우지 말고 상한을 올린다. 아래 미결 원문은 기록용.

- **U2 상한 정리가 복구 불가 판본을 지워도 되는가**: 결정 문구 그대로 하면 오래 안 쓴 DART fnltt 정정 전 판본도 지워질 수 있다. 정정 전 값은 다시 받을 수 없다.
  선택지: (가) 결정 그대로(LRU, 종류 무관), (나) 다시 받을 수 있는 것(EDINET zip·SEC Archives·DART 접수번호 원본)부터 지우고 복구 불가 판본은 마지막, (다) 복구 불가 판본은 상한에서 제외.
- **U4 앱·적재 쪽 적용 시점** — 오너 결정 불필요로 분류(`13` §4, 기본값): 검증기 먼저, 앱·적재 쪽(C3·C4·C20)은 설계 승인 뒤 앱 브랜치별(kr/app·jp/app·us/app) 별도 작업. 오너가 순서를 바꾸면 변경.

### 4.2 규칙
- **R-US1 서류·판본**: companyfacts 의 사실마다 accn 으로 서류를 붙인다. 같은 기간 같은 개념의 값이 여러 서류에 있으면 전부 RawFact 로 낸다. `is_original` = filed 가 가장 이른 것, `is_latest` = 가장 늦은 것.
  **반올림 재태깅**(나중 서류가 본문 반올림값으로 다시 태깅 — AXP 2021 총자산)은 `restated` 판정 전에 표시한다. 기준은 "먼저 공시된 값을 1억·10억·100억 단위로 반올림한 값과 정확히 같음"이다(CLAUDE.md `dropRoundedRetags`, 검증기 `:411` 독립 구현).
  표시만 하고 지우지 않는다. 쓸지 말지는 ④가 정한다.
- **R-US2 companyfacts 누락 보강**: 서류 목록에 있는 정기공시가 companyfacts 에 통째로 없으면(BE 2분기, XOM 2026-07 CIK 변경, TSM 2025 20-F) 그 서류의 인스턴스를 읽어 RawFact 를 만든다. `fetch.source = instance` 로 표시한다.
- **R-US3 본표 줄**: 줄 판단은 서류의 계산 구조(`_cal`)·표시 구조(`_pre`)로 한다. "본표에 그 줄이 있는가·어느 구역인가·부모가 무엇인가"를 `placement` 에 넣는다(CLAUDE.md "본표 기준 원칙" 2026-09-24).
  회사 고유 태그 값은 인스턴스에서 읽는다. 차원 있는 사실은 `dims` 를 남기고 본표 값으로 쓰지 않는다.
- **R-US4 기간**: `fy_key` = `fiscalYearOf(결산일)`(1월 1~7일 → 전년). 10-Q 는 3개월·누적을 `start`~`end` 로 나눈다. 20-F 는 반기 공시가 없으니 6-K 분기 재무제표(R-US7)로만 기간을 채운다.
- **R-US5 Q12 CapEx 줄**(결정 10-14): 최신 10-K/20-F 현금흐름표 **투자활동 본표 줄 중 유형자산 취득 줄**. Item `capex_ppe_line`.
  회사가 유형·무형을 **한 줄로** 적었으면 그 줄 그대로 쓰고 `mixed_with_intangible: true` 로 표시한다(NVDA·LRCX·GEV·V·MAR·DELL·DAL — `03` §2(가)). 따로 적은 무형·소프트웨어·임대장비 줄(HLT `PaymentsToAcquireSoftware`, CAT `PaymentsToAcquireEquipmentOnLease`, MCD `PaymentsToAcquireOtherProductiveAssets` = 가맹점 인수)은 넣지 않는다.
  DAL 처럼 본표에 유형 줄이 둘(FlightEquipment + OtherProductiveAssets "including technology")이면 두 줄 합이다. 줄 선택은 **태그 이름이 아니라 본표 위치와 회사 라벨**로 한다. 태그 정의는 `03` §1 원문을 쓴다.
  라벨로 판정하지 못하면(`.xsd` 내장이라 라벨 파일 없음 — MSFT·ORCL·TER) 태그 정의로만 판정하고 `label_missing` 표시를 남긴다.
- **R-US6 Q2 이자비용**: 손익 이자비용(발생주의). 원천은 손익계산서 본표 줄 또는 주석 태그(`InterestExpense` 계열 — 지금 앱 `edgar-analysis.ts:64~71` INT_EXP 6종은 **목록 참고만**, 검증기는 본표·주석 위치로 따로 판정). Item `interest_expense_pl`, 금융업(은행 레이아웃) 칸은 `out_of_scope`(Q2 ④).
- **R-US7 20-F 분기**: 6-K 연결재무보고서(HTML 표·Exhibit 99 슬라이드 아래 숨은 글자)를 문서 글자로 읽는다. 줄 대응 = 최근 20-F 라벨 파일의 같은 이름 줄. 검증기는 이미 `sixKCfYtd` 로 따로 읽는다. ①은 판독 결과를 `placement.face = false, source = 6-K` RawFact 로 낸다.
- **R-US8 외화**: 20-F 원통화 사실은 원통화 그대로 RawFact 로 낸다. USD 편의 환산 태그는 `convenience: true` 로 표시한다. 환산은 ④가 FxRate 로 한다(기간 평균·기말 — CLAUDE.md 인포맥스 방식).
- **R-US9 EPS**: 공시 희석·기본 EPS, 계속·중단 EPS 를 모두 낸다. "기본 EPS 를 계속 + 중단 합으로 채움"(A23, DELL FY2022)은 ④의 일이다. ①은 합에 필요한 두 사실이 있는지만 보장한다.
- **R-US10 주식수**: dei `EntityCommonStockSharesOutstanding`(표지·기준일), 본표 가중평균. 복수 클래스(META·DELL)는 클래스별 사실을 따로 낸다. 단위 오류(MCD 가중평균 `716.4`)는 고치지 않는다. 대신 `scale_suspect` 표시만 하고 판단은 ④에 둔다.
- **R-US11 주식 사건**: 분할 이력은 지금 Yahoo 에서 받는다. 앱도 시세를 Yahoo 에서 받으므로, 시세·분할 데이터는 앱과 같은 원천이다.
  미결(오너 확인) **U7**: 미국·일본 시세·분할 원천을 무엇으로 할지. (가) Yahoo 를 원자료로 두고 해당 칸을 "같은 원천(공통 데이터)"으로 표시, (나) SEC 공시(`StockholdersEquityNoteStockSplitConversionRatio1` 등)로 분할을 교차 확인하고 맞을 때만 독립 처리, (다) 다른 무료 시세 원천을 추가.

### 5.2 규칙
- **R-KR1 보고서·기간**: 보고서명 `(사업|반기|분기)보고서 (YYYY.MM)` 으로 (사업연도, 보고서 코드)를 정한다. 결산월은 사업보고서 월의 최빈값이다.
  12월이 아닌 결산 회사는 지금 판본을 못 정해 캐시를 쓰지 않는다(`dart.mjs:133~134·174`). 설계에서는 보고서명의 연월과 결산월로 사업연도를 정해 판본을 붙인다(사업연도 = 결산월이 속한 연도가 아니라 DART `bsns_year` 규칙 — 확인 필요(조사): 3·6·9월 결산 회사의 `bsns_year` 와 보고서명 연도의 관계).
  사업보고서 접수번호는 **보고서명의 대상 연도**로 고른다. 이듬해 목록에 지난 연도 정정본이 섞이기 때문이다(현대차 2024-03 "[기재정정]사업보고서 (2022.12)" — CLAUDE.md).
- **R-KR2 열과 판본**: 사업보고서 한 건의 당기·전기·전전기 열을 각각 RawFact 로 낸다(`column`). 같은 해가 여러 보고서에 실리면 전부 남긴다.
  `is_latest` = 그 해를 담은 가장 최근 보고서(Y+2 전전기 → Y+1 전기 → Y 당기 — CLAUDE.md 연간 로더 규칙과 같은 원칙이라 공통모드 표시). `is_original` = Y 보고서 당기.
  정정 공시(새 접수번호)로 fnltt 판본이 바뀌면 새 판본을 **추가**하고 옛 판본은 보관한다(§3.3).

### 6.2 규칙
- **R-JP1 서류**: `withdrawalStatus = 0`·`xbrlFlag = 1` 만 쓴다. 訂正은 `parentDocID` 로 원 서류에 잇는다. 訂正 중 재무제표를 다시 싣지 않은 것은 본표 사실이 없다는 표시만 한다.
  주당 값 기준일은 訂正이면 **원 서류 제출일**이다(訂正은 원 서류 숫자를 다시 싣기 때문 — 日立 2025-07 訂正, `layers.mjs:214~216`).
- **R-JP2 기간·열**: 표준 문맥 이름(`CurrentYear`·`Prior1Year` Duration/Instant, 반기 `Interim`·`Prior1Interim`·옛 `CurrentYTD`·`CurrentQuarter`)과 DEI(`CurrentFiscalYearEndDateDEI`·`CurrentPeriodEndDateDEI`·`TypeOfCurrentPeriodDEI`)로 정한다.
  `fy_key` = 결산일 연도. FY 이름(年度 표기)은 화면 문제라 ①과 무관하다(`verify-jp-design.md` D1). 결산월을 가정하지 않는다(3월·12월·8월(9983)·3월 20일(キーエンス)).
  재무상태표 열은 그 시점 자산총계가 본표에 실린 서류로 정한다(소니 IFRS 17 전환일 3열 — `verify-jp-design.md` §12 고친 결함 ①).
- **R-JP3 연결**: 연결 역할(이름에 `Consolidated`)이 있으면 연결만, 없으면 개별(`WhetherConsolidatedFinancialStatementsArePreparedDEI`). 별도 값은 `NonConsolidatedMember` 차원이다.
- **R-JP4 판본**: 같은 회계기준 서류 중 **가장 나중에 제출된** 有報·訂正이 최신이다(J-A1). 처음 공시 = 그 해 有報 당기. 회계기준(`AccountingStandardsDEI`)이 바뀐 옛 해는 그 기준 서류로만 열을 만든다.
  US GAAP 서류(キヤノン, 옛 무라타)는 본표가 문단뿐이라 본표 사실이 없다. 이것은 `out_of_scope` 다(D10).
  **U9 오너 결정(2026-10-15, `13` D29 (가))**: 한 열 = 한 서류 — 그 열의 손익계산서를 가져온 서류(정정본이면 그 판본)에서 재무상태표·현금흐름표까지. 표마다 더 최신 서류가 있어도 섞지 않는다(미국 09-25 「한 열 = 한 공시」 확장). 소니 FY2022 는 손익 = 2023-06 有報이므로 재무상태표도 2023-06 有報(2024-06 IFRS 17 재작성본 아님). ①은 지금처럼 서류별 Item 을 내고, 선택은 ④.
- **R-JP5 현금**(Q3 재결정 10-14 "q3는 1번"): Item `cash_cf_end` = 현금흐름표 「現金及び現金同等物の期末残高」(`CashAndCashEquivalents…` 개념 중 표시 구조가 `periodEndLabel` 인 기말 시점 값). 定期預金·短期投資·有価証券은 넣지 않는다.
  예: キーエンス 2026-03 = 451,269 백만엔. BS 現金及び預金 596,976 도, 앱 1,493,889 도 아니다(`08` §2).
  현금흐름표에 기말 잔액 줄이 없으면 `confirmed_absent`(BS 현금으로 대체하지 않는다).
- **R-JP6 차입금**: 본표 계산 구조에서 부채 아래 **요소 이름**이 차입금 꼴인 최상위 줄 + 리스부채(본표 → 주석 `リース負債` 포함 표시 → 재무활동 부채 변동표 산술 판정, 지금 `j2.mjs` 방식)를 쓴다. 리스 판정 불가는 `definition_blank`(일본 EV 공란 규칙).
  확인 필요(조사): 日立 차입금이 短期借入金 한 줄뿐인 것, ホンダ 0 인 것(`08` §4 — 앱 결함 후보). 검증기 판독이 이 두 회사를 어떻게 잡는지 확인한다.
- **R-JP7 Q12 CapEx 줄**: 현금흐름표 투자활동 본표 줄 중 유형 고정자산 취득 줄. 회사가 합쳐 적은 줄(「有形固定資産及び(その他の)無形資産の取得」 6종목, **「有形及び無形固定資産の取得による支出」 7974·9020·1925**)은 그 줄 그대로 쓰고 `mixed_with_intangible` 를 표시한다.
  따로 적은 무형·임대자산 줄(7203 「賃貸資産の購入」)은 넣지 않는다(`03` §6). 판정은 라벨 문자열이 아니라 **요소 이름 + 본표 위치**를 먼저 보고, 회사 고유 요소면 라벨을 본다. 라벨 정규식 하나에 기대면 `有形及び無形` 같은 줄을 놓친다(지금 앱 `jp-ev.ts:375`).
- **R-JP8 Q2 이자비용**(결정 ②③④, 실측 `05`·`06` (나)(다)):
  - 손익 「支払利息」: J-GAAP `jppfs_cor:InterestExpensesNOE`(영업외비용), IFRS `jpigp_cor:InterestExpensesIFRS`(본표 또는 금융비용 주석).
  - 社債利息·CP利息 등 따로 적은 이자 줄은 더한다(결정 ② — セブン&アイ). JR東海 「鉄道施設購入長期未払金利息」도 손익 이자 줄이면 더한다. 확인 필요(조사): 그 줄이 손익 본표에 있는지 확인.
  - 합계 줄이 없는 IFRS 회사: 金融費用 내역 표의 **「支払利息」 소제목 아래 태그된 구성요소**만 합산한다(상각후원가 금융부채·리스·社債 이자, 소제목 안 「その他」 = `OtherInterestExpensesIFRS`).
    소제목 밖 「その他」(`OtherFinanceCostsIFRS`)는 넣지 않는다. 구성요소 판정은 인라인 XBRL 표 행(사람이 읽는 줄)으로 확인한다. 대상: キオクシア·中外·第一三共·ソニー·三菱重工·NTT·JT·デンソー·KDDI·武田 FY2026.
  - CF 조정 支払利息만·金融費用만(リクルート·トヨタ·三菱商事)·支払利息 줄 없음(キーエンス·ファナック·東京エレクトロン — 차입금·사채 0 확인) → `definition_blank`. CF 값으로 대체하지 않는다.
  - US GAAP(キヤノン) → `out_of_scope`. 금융업(은행·日本郵政·東京海上 등 BNK·INS 서식) → `out_of_scope`(결정 ④).
  - 값은 절댓값으로 정규화하지 않는다. 원 부호를 RawFact 에 두고, ソフトバンク 9434 처럼 △ 태깅된 것은 `sign` 표시만 한다. 부호 처리는 ④가 한다.
  - **U10 오너 결정(2026-10-15, `13` D28 (가))**: 분모 = 金融費用 안 이자만. 営業費用 안 금융사업 이자(ソニー·KDDI·NTT 은행업 등)는 분자 영업이익에서 이미 빠졌으므로 넣지 않는다. ①은 그 이자 줄을 RawFact 로 남기되 Item `interest_expense_pl` 에 넣지 않고, Item 에 `excluded_operating_finance_interest`(금액·근거 fact) 표시 — 화면 사유 「금융사업 이자는 영업비용에 포함 — 분모 제외」의 근거.
- **R-JP9 주식수**: 그 사업연도 有報의 株式の総数等(기말 발행주식수) − 自己株式等 표 제출회사 행(자기 명의 + 타인 명의). 提出日現在発行数도 낸다(기말 뒤 권리락 분할 확인용 — 三菱重工 2024-03·信越 2023-03).
- **R-JP10 EPS**: 경영지표(`jpcrp_cor` SummaryOfBusinessResults)의 희석 EPS, 「－」(nil)면 기본 EPS. 본표 EPS 도 따로 낸다. 서류 제출일을 같이 남긴다(분할 계수 계산 기준).
- **R-JP11 금융 서식**: 손익 요소에 BNK·INS·SEC 가 있으면 `financial_format` 표시. 금융 레이아웃(17행) 입력이다.

### 6.3 실패 처리(일본 고유)
- 날짜 목록: status ≠ 200·건수 불일치·JSON 아님 → `fetch_failed`, 저장 안 함. 범위 밖 날짜(status 404)도 저장하지 않는다.
- 서류: zip 자리에 JSON 오류(HTTP 200 + metadata 오류) → `fetch_failed`. 압축 해제·인스턴스 없음 → `parse_failed`.
- 날짜 목록 하루라도 실패하면 그 실행의 모든 일본 종목에 `fetch_failed` 사유를 단다. "서류 없음"으로 판정하지 않는다.

## 7. 테스트 방법 (①단계 완료 조건)

memory `feedback-verifier-rework-zero-error`: 단계 완료 = 옛 검증기 결과 대조 + 세 시장 심은 오류 시험 + 독립 감사(Opus, 최종 Fable). 작성자는 스스로 승인하지 않는다.

1. **T1 판독 고정 시험(골든셋)**: 위 §4.4·§5.4·§6.4 사례마다 원본 조각(필요한 XBRL 사실·원문 표·JSON 행)과 기대 RawFact·Item 을 git 파일로 둔다. 운영 DB 에는 넣지 않는다(memory `feedback-db-capacity` — 골든셋은 git 파일).
   큰 원본(EDINET zip 수십 MB)은 git 에 넣지 않고 캐시 파일 sha256 만 적는다. 크기 기준은 구현 전에 오너 보고.
2. **T2 오프라인 재현**: 소켓을 막은 채(외부 요청 시 즉시 실패) 두 번 실행해 출력 md5 가 같고 외부 요청이 0건인지 본다. 측정 문서 `05`~`08` 이 이미 쓴 방법이다.
3. **T3 요청 수**: 첫 실행·두 번째 실행의 원천별 요청 수를 FetchLog 로 보고한다. 두 번째는 갱신형(목록·companyfacts) 몇 건만 남아야 한다.
4. **T4 옛 검증기 대조**: 미국 47(2호기 `/tmp/full-us-1011.log` 실행분)·한국 30·일본 42 종목에서 지금 검증기 A층이 읽은 원자료 값과 새 ① 출력이 같은지 칸마다 본다. 다르면 어느 쪽이 원문과 맞는지 원문 위치(locator)로 가린다. 측정 문서 값(`03`·`05`~`08` 의 원 단위 표)도 같은 방식으로 대조한다.
5. **T5 심은 오류(⑨ 공통 틀의 ① 부분)**: 캐시에 틀린 입력을 넣었을 때 ①이 잡아야 한다.
   - 깨진 zip·잘린 JSON
   - DART 020·800·013(목록에 보고서 있음/없음 두 경우)
   - KRX 거래일 빈 응답
   - EDINET status 404·HTTP 200 + JSON 오류
   - SEC 429 연속
   - 표 단위를 천원 → 원으로 바꿈
   - negatedLabel 제거
   - 같은 칸 후보 하나 추가(ambiguous)
   - 정정 공시 도착(새 판본 추가 + 옛 판본 유지 확인)
   - 5GB 초과(정리 건수 기록 확인)
   - 공유 보관소에 엉뚱한 공시를 그 번호로 심음(신원 확인이 잡고 quarantine·검증불가 확인)
   - 끝이 잘린 XML·CRC 틀린 zip 저장 시도(저장 거부 확인)
   - 앱과 검증기가 다른 갱신형 판본을 씀(판본 차이로 분류되는지 확인)
6. **T6 독립성 정적 검사**: `src/` 경로 import·read 0건, 공유 보관소 밖 앱 캐시 경로(파생 파일·DB 저장본) 읽기 0건, 공유 보관소의 원본을 읽는 곳은 모두 신원 확인 함수를 거치는지를 검사로 막는다. 실행 전 no-undef 검사와 대표 1종목 실행을 먼저 한다(memory `feedback-verifier-precheck`).
7. **T7 알려진 오류 검출**: `00-handoff.md` 측정 항목(079550 리스 단위, D1~D3, DELL 기본 EPS)과 새로 찾은 결함(서진시스템 EPS 계속영업, 日立·ホンダ 차입금, 엘에스일렉트릭 FY2025 리스이자, 7974·9020·1925 CapEx)이 ①출력 → ④ → ⑥ 으로 실패나 불일치가 되는지 본다. ⑥ 은 `12` 문서 범위이고, ①은 필요한 사실을 내는지까지 확인한다.
